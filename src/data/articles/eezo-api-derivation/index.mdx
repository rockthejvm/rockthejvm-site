## Introduction

As we introduced in [Introducing Eezo: Next-gen Scala Web Framework](https://rockthejvm.com/articles/introducing-eezo), Eezo is a modern web framework for Scala 3 that aims to simplify web development by leveraging the latest features of the language. In the previous article, we covered how to set up an Eezo project and how to build a working web application backed by Postgres. However, not all the applications deserve a UI. Most of backend services only need an API to interact with clients or other services. In this article, we will explore how Eezo can help us build APIs efficiently. As a bonus, we'll also introduce how to manage an application configuration, using Eezo's built-in configuration management system.

## Setting Up Eezo

At the time of writing, the latest version of Eezo is 0.4.2. Make sure to use this version to ensure compatibility with the examples in this article.

As we did in the previous article, let's start by setting up an Eezo project. Let's say you already have an Eezo project initialized. If not, you can follow the instructions in the [Setting Up Eezo](https://rockthejvm.com/articles/introducing-eezo#setting-up-eezo) section to set up a new project. Last versions also added the possibility to scaffold a new project from an empty folder:

```bash
eezo new .
```

The command above will scaffold a new Eezo project in the current folder. It will create the necessary directory structure and configuration files to get started with Eezo.

We'll implement some JSON APIs. So, we need a way to serialize and deserialize JSON data. Current versions of Eezo use [upickle](https://com-lihaoyi.github.io/upickle/) for JSON handling. Eezo has a dedicated module for this:

```scala
libraryDependencies += "io.eezo" %% "eezo-upickle" % "0.4.2"
```

The modular approach we chose allows us to add more JSON parsers or other serialization libraries in the future without affecting the core framework.

The configuration module is already included in Eezo, so we don't need to add any additional dependencies for it. So, without any further setup, we can move implementing our API and managing the application configuration.

## Deriving APIs

The mantra of Eezo is that the model is the central piece of our application. In other words, we define our domain models first, and then we expose them through APIs. So, first, let's define a simple domain model for a `Book` inside the `models` package:



```scala
package models

import io.eezo.db.Table
import io.eezo.core.Id

case class Book(id: Id[Book], title: String, author: String) derives Table
```

As you can see, we already put the `Table` derivation to the model. First, you add the model to the known schemas:

```scala
import io.eezo.EezoApp
import io.eezo.db.Schema
import io.eezo.generated.Routes
import io.eezo.http.RouteTable
import models.Book


object AppSchema extends Schema {
  val books = table[Book]
}

object Main extends EezoApp {
  override def schema: Schema     = AppSchema
  override def routes: RouteTable = Routes.table()
}
```

Once we have defined our schema and main application object, the TUI spawned by the new version of the `eezo dev` command will warn us that there is a drift between the defined schema and the actual database schema:

![Schema drift](./images/schema-drift.png)

We can press `s` and accept the suggested changes to synchronize the database schema with our defined schema. This ensures that the `books` table is created in the database according to our `Book` model:

![Schema Ok](./images/schema-ok.png)

Now that we have synchronized our database schema with the defined schema, we can proceed to implement the APIs for managing `Book` entities. First let's focus on creating a simple CRUD API for `Book`. Eezo derives CRUD APIs from a model by just deriving the `Api` type class:


```scala
import io.eezo.http.Api

case class Book(id: Id[Book], title: String, author: String) derives Table, Api
```

If we look at our TUI will see that it's complaining with the following error:

```text
7 |case class Book(id: Id[Book],
 title: String, author: String) derives Table, Api
   |                                           ^
   |No Serde instance for models.Book. Add eezo-upickle to the build and import
 io.eezo.json.upickle.given, or write a given api.Serde[models.Book]
```

As usual, Eezo errors are very descriptive and guide us on how to fix the issue. In this case, it tells us that we need a `Serde` (serializer/deserializer) instance for our `Book` model. We can resolve this by importing the necessary given instances:

```scala
import io.eezo.json.upickle.given
```

Adding the import fixes the compilation error. Now, the `routes` tab of the TUI lists the automatically derived CRUD routes for the `Book` model, allowing us to interact with the `books` table through the generated API endpoints:

![Routes tab showing CRUD routes for Book](./images/api-routes.png)

As we can see, the autogenerated CRUD routes are mounted under the `/api` path, to distinguish them from other potential routes in the application.

First, we can start inserting some books into the database using the POST endpoint `/api/books`. We need to provide a JSON payload with the `title` and `author` fields, as the `id` will be automatically generated by the database. For example:

```bash
curl -i -X POST http://localhost:8080/api/books \
  -H "Content-Type: application/json" \
  -d '{"title":"Dune","author":"Frank Herbert"}'
```

Eezo will respond with a 201 HTTP response with the details of the newly created book, including the automatically generated `id` field in the `Location` header. The response will look something like this:

```text
HTTP/1.1 201 Created

Server: Jetty(12.1.11)
Date: Mon, 09 Nov 2026 20:13:46 GMT
Location: /api/books/9d798074-c572-4694-8706-f10e3cbe273a
Content-Type: application/json; charset=utf-8
Content-Length: 85

{"id":"9d798074-c572-4694-8706-f10e3cbe273a","title":"Dune","author":"Frank Herbert"}
```

We can now retrieve the list of books using the GET endpoint `/api/books`. This will return a JSON array containing all the books in the database. For example:

```bash
curl -i http://localhost:8080/api/books
```

The response will look something like this:

```text
HTTP/1.1 200 OK
Server: Jetty(12.1.11)
Date: Mon, 09 Nov 2026 20:15:00 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 87

[{"id":"9d798074-c572-4694-8706-f10e3cbe273a","title":"Dune","author":"Frank Herbert"}]
```

Everything is working as expected. The first API call successfully created a new book, and the subsequent GET request retrieved the list of books, confirming that the book was stored in the database.

Eezo chooses to have also an opinionted way to represent errors in the API responses. In fact, it implements the standard [RFC 9457](https://www.rfc-editor.org/info/rfc9457/), called "Problem Details". We can try to insert a book with missing required fields to see how the error is represented:

```bash
curl -i -X POST http://localhost:8080/api/books \
  -H "Content-Type: application/json" \
  -d '{"title":"Dune"}'
```

The response will look something like this:

```text
HTTP/1.1 422 Unprocessable Entity
Server: Jetty(12.1.11)
Date: Mon, 09 Nov 2026 20:27:04 GMT
Content-Type: application/problem+json
Content-Length: 163

{
  "type": "about:blank",
  "title": "Unprocessable Content",
  "status": 422,
  "detail": "missing keys in dictionary: author at $",
  "instance": "/api/books"
}
```

We can notice two things from this response. First, the response content type is `application/problem+json`, indicating that it follows the Problem Details standard. Second, the response provides detailed information about the error, including the missing required field and the instance of the request that caused the error. The fields of the JSON are the standard fields defined by the Problem Details specification: `type`, `title`, `status`, `detail`, and `instance`. If you're asking what the `$` symbol in the `detail` field means, it is the JSONPath representation of the root of the JSON document where the error occurred.

Can we create create also custom API endpoints, not just the automatically derived CRUD routes? The answer is yes. Eezo allows us to define custom routes alongside the derived ones, giving us full control over the API surface.
