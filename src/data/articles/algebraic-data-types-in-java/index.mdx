## Introduction

Every Java developer has been there. We return a `List<Job>` from a search service, and suddenly we are not sure what an empty list means. Is there no data? Did the query fail? Was the query too broad?

We add a status field. Then a nullable `Integer estimatedCount`. Then someone adds another status code, and nobody updates the Javadoc.

Before long, we have a data structure where only some fields are meaningful depending on the value of some other field, and the compiler has nothing to say about it.

Fortunately, _Algebraic Data Types_, or ADTs, are the answer to this problem. They are a pattern for modeling data so that **illegal states are not representable**.

They come from functional programming languages like Haskell and [Scala](/articles/algebraic-data-types-in-scala), but modern Java provides everything we need to use them directly through records and sealed interfaces.

In this article, we will look at what ADTs are, how to express them in Java 25, and why they make our domain models more correct and a lot easier to work with. All we need to follow along is Java 25 and a text editor. So, without further ado, let's get started.

:::note
All features used in this article were finalized between Java 14 and Java 21. Java 25, as the current LTS release, is the recommended target, but any Java 21+ project can follow along.
:::

## The Problem With the Old Approach

Let's start with a concrete example. We are building a job search service.

The search can produce three different outcomes: it finds results, it finds nothing, or the query is so broad that we refuse to run it and return an estimate of how many results there would be.

### The Nullable-Fields Trap

The classic Java approach is to return a result object with several fields:

```java
class JobSearchResult {
    private final String status;          // "FOUND", "NO_MATCHES", "TOO_BROAD"
    private final List<Job> jobs;         // only meaningful when status is "FOUND"
    private final Integer estimatedCount; // only meaningful when status is "TOO_BROAD"

    // constructor, getters...
}
```

**This works, but it has a lot of problems**. The `jobs` field is null when the status is `"NO_MATCHES"`. The `estimatedCount` field is null when the status is `"FOUND"`.

The compiler does not know any of this. It will happily let us call `result.getJobs().size()` without checking the status first, and we get a `NullPointerException` at runtime (every Java developer's old friend).

The invariant "if status is X, then field Y is populated" lives only in a comment. The compiler cannot enforce it.

### The Open Hierarchy Trap

A second approach is to use a class hierarchy:

```java
class JobSearchResult {}
class FoundResult extends JobSearchResult       { private final List<Job> jobs;        /* ... */ }
class NoMatchesResult extends JobSearchResult   {}
class QueryTooBroadResult extends JobSearchResult { private final int estimatedCount; /* ... */ }
```

This is better because each subclass carries only the fields that make sense for it. However, the hierarchy is open.

**Anyone can add a fourth subclass anywhere in the codebase**. When we write a consumer, the compiler gives us no guarantee that we covered all the cases:

```java
String describe(JobSearchResult result) {
    if (result instanceof FoundResult found) {
        return "Found " + found.getJobs().size() + " jobs.";
    } else if (result instanceof NoMatchesResult) {
        return "No jobs matched your query.";
    }
    // We forgot QueryTooBroadResult. The compiler says nothing.
    return "";
}
```

We need a way to tell the compiler: there are exactly three possible outcomes, and every consumer of a `JobSearchResult` must handle all three. Records and sealed interfaces give us exactly that.

## Product Types: Records

As usual, we'll start with the building blocks before we get to the full solution. The first one is the _product type_.

**A product type is a type that bundles several fields into one value.**

### Why Not a Plain Class?

Before records, a Java developer would reach for a plain class to represent a simple value like a search query:

```java
class SearchQuery {
    private String keyword;

    public SearchQuery(String keyword) {
        this.keyword = keyword;
    }

    public String getKeyword() { return keyword; }
}
```

This approach has several problems. The field is mutable by default. Marking it `final` prevents reassignment, but we must remember to do so. Nothing in the language enforces it.

We must also write `equals()`, `hashCode()`, and `toString()` by hand, or leave them incorrect. The class is verbose, and nothing prevents partial construction if we add more fields later.

So, are we doomed to write all this boilerplate forever?

### What Records Give You

Java 16 introduced **records as a first-class way to express product types**. The same `SearchQuery` becomes:

```java
record SearchQuery(String keyword) {}
```

A single record declaration gives us all of the following automatically:

- A constructor that sets all fields
- Immutable fields (declared `final` by the compiler)
- `equals()` and `hashCode()` based on all components
- `toString()` that includes every field
- Accessor methods named after the fields (e.g., `keyword()`, not `getKeyword()`)

:::note
Record immutability is reference immutability: the fields cannot be reassigned, but if a field holds a mutable object such as a `List`, the contents of that object can still be changed. To achieve deep immutability, use unmodifiable wrappers or immutable collection types.
:::

We can model a job posting with the same approach. First, let's define the small domain records we'll build on for the rest of the article:

```java
record JobId(long value) {}
record Company(String name) {}
record Role(String title) {}
record Salary(double amount) {}
```

Now the `Job` record is a product of all four:

```java
record Job(JobId id, Company company, Role role, Salary salary) {}
```

In type algebra, we write it as:

Job = JobId × Company × Role × Salary

If `JobId` has N possible values and `Company` has M possible values, then `Job` has N × M × (values of `Role`) × (values of `Salary`) possible values. The total grows by multiplication. That is why we call this a product type.

:::note
Records were finalized in Java 16 under [JEP 395](https://openjdk.org/jeps/395).
:::

## Sum Types: Sealed Interfaces

The second building block is the _sum type_. Where a **product type uses AND** (a `Job` has an `id` AND a `company` AND a `role` AND a `salary`), a **sum type uses OR**.

Imagine we are modeling the outcome of looking up a single job by its id. There are exactly two outcomes: we either find the job, or we do not. A sum type expresses this:

```java
sealed interface JobLookupOutcome
    permits JobAvailable, JobMissing {}

record JobAvailable(Job job) implements JobLookupOutcome {}
record JobMissing(JobId id) implements JobLookupOutcome {}
```

The `sealed` keyword is the key ingredient. It tells the compiler that `JobLookupOutcome` can only be one of the types listed in `permits`. No other class or interface outside the same package (or named module) may implement or extend it.

:::note
Sealed classes were finalized in Java 17 under [JEP 409](https://openjdk.org/jeps/409).
:::

In type algebra:

```text
JobLookupOutcome = JobAvailable + JobMissing
```

The number of possible `JobLookupOutcome` values is the number of possible `JobAvailable` values PLUS the number of possible `JobMissing` values. That is where the name "sum type" comes from.

### Sealed Hierarchies

Let's look at the rules in detail. The `sealed` modifier closes a type hierarchy at compile time. Only the types in `permits` may implement the interface. **Every permitted subtype must live in the same package or in the same-named module**.

Each permitted subtype must also carry one of three modifiers. The `final` prevents further subclassing. `sealed` allows it via its own `permits` list. `non-sealed` reopens the hierarchy, removing the compiler guarantee for that branch.

```java
sealed interface JobAlert permits MatchAlert, SystemAlert, CustomAlert {}

// final: closed leaf — no class may extend MatchAlert
// Records are implicitly final, so the modifier is not written explicitly.
record MatchAlert(Job job) implements JobAlert {}

// sealed: controlled extension — only ExpiryAlert and QuotaAlert are permitted
sealed interface SystemAlert extends JobAlert
    permits ExpiryAlert, QuotaAlert {}
record ExpiryAlert(JobId id)  implements SystemAlert {}
record QuotaAlert(int limit)  implements SystemAlert {}

// non-sealed: the hierarchy is reopened — any class may extend CustomAlert
non-sealed abstract class CustomAlert implements JobAlert {
    abstract String message();
}
```

`MatchAlert` is a `record`, so the `final` keyword is implicit. `SystemAlert` is itself `sealed`, adding a second controlled layer to the hierarchy. `CustomAlert` is `non-sealed`, which is an escape hatch: downstream code may extend it freely, but the compiler no longer guarantees exhaustiveness for that branch.

The `permits` clause is exhaustive in both directions. The compiler rejects a subtype that extends the sealed type but is not listed, and rejects a `permits` entry that does not extend the sealed type.

These rules give the compiler a complete, verified picture of every shape the sealed type can take. That picture is what makes exhaustiveness checking in switch expressions work.

### Sealed Interfaces vs Enums

At this point, a reasonable question comes up. Java already has enums, and they also define a closed set of cases that the compiler can check exhaustively in a switch. So why reach for a sealed interface at all?

The first answer that comes to mind is that an enum cannot carry data. **That answer is wrong**. An enum carries data just fine:

```java
enum JobCategory {
    ENGINEERING("Building the product."),
    DESIGN("Shaping the experience."),
    SALES("Closing the deals.");

    private final String description;

    JobCategory(String description) {
        this.description = description;
    }

    String description() { return description; }
}
```

Enums can go a lot further than that. In fact, each constant may declare its own body, with its own fields and its own overrides. To see it, let's model how a job posting quotes its pay. Job ads express salaries per hour, per month, or per year, and we want a yearly figure so that we can compare them:

```java
enum PayPeriod {
    HOURLY {
        private final int workingHoursPerYear = 1_800;

        @Override
        Salary toYearly(Salary salary) {
            return new Salary(salary.amount() * workingHoursPerYear);
        }
    },
    MONTHLY {
        @Override
        Salary toYearly(Salary salary) {
            return new Salary(salary.amount() * 12);
        }
    },
    YEARLY {
        @Override
        Salary toYearly(Salary salary) {
            return salary;
        }
    };

    abstract Salary toYearly(Salary salary);
}
```

**Every constant with a body is an anonymous subclass of the enum type**. The `HOURLY` constant holds a `workingHoursPerYear` field that `MONTHLY` and `YEARLY` know nothing about, and each constant implements `toYearly` in its own way.

So, what has to stay the same across the constants? Only the API we can call from the outside. Every call on a `PayPeriod` value must resolve against a member declared on the `PayPeriod` type itself, which here means `toYearly` and nothing else. **An enum lets each constant keep its own internals, but it exposes a single API to its callers**.

The reason is that the anonymous subclass created for a constant has no name we can write down. Nothing stops us from declaring a method that only one constant owns:

```java
enum PayPeriod {
    HOURLY {
        private final int workingHoursPerYear = 1_800;

        int hoursPerYear() { return workingHoursPerYear; } // only HOURLY has it

        @Override
        Salary toYearly(Salary salary) {
            return new Salary(salary.amount() * hoursPerYear()); // fine, we're inside the body
        }
    },
    // Omissis
}
```

The `hoursPerYear` method is real, and the body of `HOURLY` calls it without any problem. From the outside, though, the static type of `PayPeriod.HOURLY` is `PayPeriod`, and `hoursPerYear` is not a member of `PayPeriod`:

```text
error: cannot find symbol
        System.out.println(PayPeriod.HOURLY.hoursPerYear());
                                           ^
  symbol:   method hoursPerYear()
  location: variable HOURLY of type PayPeriod
```

:::note
Unfortunately, no cast rescues us here. At runtime, `PayPeriod.HOURLY.getClass()` returns `PayPeriod$1`, a class the language gives us no way to name. Since we cannot write the type, we cannot call anything the type adds.
:::

**This is exactly where a sealed interface differs**. Its variants are types with names, so once we know which variant we hold, we can call whatever that variant adds.

A sealed interface, then, is a fixed set of subtypes. Each variant is a real type that we instantiate freely, and each one exposes its own components:

```java
sealed interface JobSearchOutcome
    permits Found, NoMatches, QueryTooBroad {}

record Found(List<Job> jobs) implements JobSearchOutcome {} // holds a list
record NoMatches() implements JobSearchOutcome {}           // holds nothing
record QueryTooBroad(int estimatedCount) implements JobSearchOutcome {} // holds an int
```

Here, `Found` exposes a `jobs()` accessor that `QueryTooBroad` does not have, and there is an unbounded number of `Found` values, one for every possible list of jobs. **An enum fixes the set of values. A sealed interface fixes the set of types.**

In the type algebra we already used, an enum is a sum of nullary cases:

```text
JobCategory = ENGINEERING + DESIGN + SALES
```

Each term counts as exactly one value. We should be precise here, because this is a statement about _how many values the type has_, not about how much data hangs off each constant. The `description` we attached to every `JobCategory` adds no new value to the type. There are still exactly three of them. **That description is a function from a constant to a `String`**, which is how a language like Haskell would model it in the first place.

A sealed interface, instead, is a sum of products, where each variant is a product of several fields and can have unboundedly many values. Counting values alone, an enum is the degenerate case of a sum type: every variant contributes exactly one.

So, how do we choose between the two? Let's ask ourselves two questions.

The first one is how many values each case needs. If one fixed instance per case is enough, an enum is the natural fit. If a case must exist in many instances, such as one `Found` for every possible list of jobs, then we need a sealed interface.

The second one is whether the cases need different shapes. If every case exposes the same API, an enum works, even when the cases carry data. If one case must expose a field or a method that the others do not, we reach for a sealed interface.

## Hybrid Types: Sealed Interfaces with Records

Now we can put both building blocks together. Let's model our original job search outcome properly:

```java
sealed interface JobSearchOutcome
    permits Found, NoMatches, QueryTooBroad {}

record Found(List<Job> jobs) implements JobSearchOutcome {}
record NoMatches() implements JobSearchOutcome {}
record QueryTooBroad(int estimatedCount) implements JobSearchOutcome {}
```

This pattern is known in functional programming literature as a _sum of products_. The sealed interface is the sum (one of exactly three things). Each record is a product (a set of fields).

Each variant carries exactly the fields that make sense for it. The `Found` type has a list of jobs. `NoMatches` has no fields at all. The absence of results is the whole message.

`QueryTooBroad` has an estimate but no job list. There are no nullable fields. There is no "this field is only meaningful when the status is X" in a comment.

Let's see the service that produces this type:

```java
class JobSearchService {

    private static final int MAX_RESULTS = 1_000;

    JobSearchOutcome search(SearchQuery query) {
        int estimated = repository.estimateMatches(query.keyword());
        if (estimated > MAX_RESULTS) {
            return new QueryTooBroad(estimated);
        }
        List<Job> results = repository.find(query.keyword());
        if (results.isEmpty()) {
            return new NoMatches();
        }
        return new Found(results);
    }
}
```

So far, so good. **The return type tells the whole story**. A caller looking at the `search(...)` function immediately knows that exactly three things can come back, and each has a defined shape. No Javadoc needed to explain which fields are populated when.

Now we have a well-defined hybrid type. The next step is to consume it safely.

## Pattern Matching on ADTs

Java gives us three tools for consuming ADTs: switch expressions, pattern matching, and record patterns. Each builds on the previous. Together, they let the compiler verify that every variant is handled.

### Switch Expressions

**A switch expression is a switch that returns a value**, not just a control-flow statement.

The arrow syntax (`->`) eliminates fall-through and makes each branch return directly. The compiler also requires that all possible values are covered.

Why an `enum` here? We chose it on purpose. A switch expression works on any closed set of values, and an enum is the simplest one to reason about. We can also switch over a sealed interface, but picking out each variant relies on pattern matching for switch, a separate feature we get to next. Introducing them one at a time keeps it clear which Java version gives us what.

Here is an example that maps each `JobCategory` to the `PayPeriod` job ads usually quote for it. Both enums come from the previous section:

```java
PayPeriod defaultPayPeriod(JobCategory category) {
    return switch (category) {
        case ENGINEERING -> PayPeriod.YEARLY;
        case DESIGN      -> PayPeriod.YEARLY;
        case SALES       -> PayPeriod.MONTHLY;
    };
}
```

If we remove one of the cases, the compiler refuses to compile:

```text
error: the switch expression does not cover all possible input values
```

:::note
Switch expressions were finalized in Java 14 under [JEP 361](https://openjdk.org/jeps/361).
:::

The same exhaustiveness guarantee applies to sealed interfaces. Here is the `JobLookupOutcome` type from earlier, consumed with a switch expression:

```java
String status(JobLookupOutcome outcome) {
    return switch (outcome) {
        case JobAvailable available -> "The job is available.";
        case JobMissing missing     -> "The job is no longer listed.";
    };
}
```

There is no `default` branch, and none is needed. The `permits` clause already tells the compiler the list of variants is complete, so it checks exhaustiveness the same way it did for the enum. Each `case` names a variant type instead of a constant. That is pattern matching for switch, which we unpack in the next section.

### Pattern Matching

Pattern matching for `instanceof` removes the need for explicit casts. **We can test the type and bind a variable in a single step**:

```java
Object obj = getResult();
if (obj instanceof String s) {
    System.out.println(s.length());
}
```

The variable `s` is already of type `String` inside the block. No explicit cast is needed.

We can lift this into a switch expression to match on multiple types in a single construct:

```java
String format(Object value) {
    return switch (value) {
        case Integer i -> "Int: " + i;
        case String s  -> "Str: " + s;
        default        -> "Other";
    };
}
```

:::note
Pattern matching for `instanceof` was finalized in Java 16 under [JEP 394](https://openjdk.org/jeps/394).
Pattern matching for switch was finalized in Java 21 under [JEP 441](https://openjdk.org/jeps/441).
:::

### Record Patterns

Record patterns go one step further. Inside a switch case, **we can destructure a record inline**. The compiler automatically extracts the record's components, eliminating the need to call the accessor methods explicitly.

Here is the `JobLookupOutcome` switch written with record deconstruction:

```java
String describe(JobLookupOutcome outcome) {
    return switch (outcome) {
        case JobAvailable(Job job) -> "Found job: " + job.role().title();
        case JobMissing(JobId id)  -> "No job found with id " + id.value();
    };
}
```

The case `JobAvailable(Job job)` syntax matches a `JobAvailable` value and binds its `job` component to a local variable. The code is shorter and reads closer to the domain.

**Record patterns also work with nested types**. A `JobAvailable` holds a `Job`, which itself holds a `Role`. We can destructure both in a single case if needed.

:::note
Record patterns were finalized in Java 21 under [JEP 440](https://openjdk.org/jeps/440).
:::

The same tools work on hybrid types. Here is the consumer for `JobSearchOutcome`, the type we defined in the previous section:

```java
String describe(JobSearchOutcome outcome) {
    return switch (outcome) {
        case Found f         -> "Found " + f.jobs().size() + " jobs.";
        case NoMatches n     -> "No jobs matched your query.";
        case QueryTooBroad q -> "Your query is too broad (~" + q.estimatedCount() + " matches). Please refine it.";
    };
}
```

Congratulations! We have just defined and consumed our first Algebraic Data Type in Java.

As we can see, the switch is an expression: it returns a value. The compiler checks that all three variants are handled. Inside each branch, we get a typed reference to the specific variant.

In the `Found f` branch, `f.jobs()` is available. In the `QueryTooBroad q` branch, `q.estimatedCount()` is available. Fields that do not apply to a variant are not reachable from that branch. That is the whole point.

Because the set of variants is closed, **the compiler verifies exhaustiveness**. If we forget a branch, the compiler refuses:

```text
error: the switch expression does not cover all possible input values
```

This is the safety net we were missing with the open class hierarchy. When we add a new variant, the compiler walks us to every place in the codebase that needs updating.

We stop relying on code review or tests to catch a forgotten case. The language enforces it for us.

## The Pattern Generalizes: `Result<T, E>`

Once we see this shape, we start seeing it everywhere. A very common version of it is a generic success-or-failure type. We want to express that an operation either returned a value of type `T` or failed with an error of type `E`:

```java
sealed interface Result<T, E>
    permits Success, Failure {}

record Success<T, E>(T value) implements Result<T, E> {}
record Failure<T, E>(E error) implements Result<T, E> {}
```

This is the same pattern as `JobSearchOutcome`, lifted to two type parameters. `Success` carries a `T`. `Failure` carries an `E`. To tell the truth, Java makes us pay a small tax here, and the following note explains exactly why.

:::note
Both `Success<T, E>` and `Failure<T, E>` carry both type parameters, even though each record only uses one of them.

Java generics are invariant: `List<String>` is not a subtype of `List<Object>`, even though `String` is a subtype of `Object`. Invariance means the type parameter does not carry subtyping information across generic types.

Languages with declaration-site variance (Scala uses `+T`, Kotlin uses `out T`) can mark a type parameter as covariant. With covariance, if `A` is a subtype of `B`, then `Box<A>` is a subtype of `Box<B>`.

Java has no declaration-site variance.

Because Java lacks covariance, both `Success` and `Failure` must carry both `T` and `E`.

Without `E` on `Success`, the expression `new Success<>(job)` has type `Success<Job>`. That is not assignable to `Result<Job, JobLookupError>`.

The compiler cannot prove compatibility without the second parameter present on both records.
:::

Let's define a concrete error type for job lookups as a sum type:

```java
sealed interface JobLookupError
    permits JobNotFound, DatabaseUnavailable {}

record JobNotFound(JobId id) implements JobLookupError {}
record DatabaseUnavailable(String reason) implements JobLookupError {}
```

Let's see a repository method that uses Result with this error type:

```java
class JobRepository {

    Result<Job, JobLookupError> findById(JobId id) {
        Job job = database.get(id);
        if (job == null) {
            return new Failure<>(new JobNotFound(id));
        }
        return new Success<>(job);
    }
}
```

And the caller that consumes the result:

```java
String loadJobDescription(JobId id) {
    return switch (repository.findById(id)) {
        case Success<Job, JobLookupError>(Job job) ->
            "Role: " + job.role().title();
        case Failure<Job, JobLookupError>(JobLookupError error) ->
            switch (error) {
                case JobNotFound(JobId jobId)           -> "No job found with id " + jobId.value();
                case DatabaseUnavailable(String reason) -> "Service unavailable: " + reason;
            };
    };
}
```

Exhaustiveness still works. The compiler still refuses to let us forget a branch. The only new thing is generics; the pattern itself is identical.

## Why "Algebraic"?

At this point, a fair question is: why are these types called "algebraic"?

**An algebra is a set of objects and one or more operations to combine them into new objects of the same set**. In numeric algebra, the objects are numbers and the operations are +, -, ×, and /.

For ADTs, the objects are the standard Java types, and the record and sealed-interface constructors are the operators. They let us build new types from existing ones.

We already used two operations:

- Records are products. `Job` = `JobId` × `Company` × `Role` × `Salary`.
- Sealed interfaces are sums (also called coproducts). `JobSearchOutcome` = `Found` + `NoMatches` + `QueryTooBroad`.

We can define the complexity of a type as the number of values it can represent. **Well-designed types have the least complexity they need** to model the information they carry.

Here is a concrete example. Suppose we need to model a set of mutually exclusive configuration options, `A`, `B`, or `C`. A naive product type would be:

```java
record Config(boolean a, boolean b, boolean c) {}
```

This type has 2 × 2 × 2 = 8 possible values. In fact, only three of them are valid: `Config(true, false, false)`, `Config(false, true, false)`, and `Config(false, false, true)`.

The other five are invalid states that our code has to defend against.

A sum type solves this directly:

```java
sealed interface Config permits A, B, C {}
record A() implements Config {}
record B() implements Config {}
record C() implements Config {}
```

This type has exactly three possible values. The five invalid states cannot be constructed. The compiler eliminates them at the type level. As we said, illegal states should not be representable at all.

We can apply the same thinking to our `Failure` type. Imagine we had used a raw `String` as the error type instead of a typed sum type:

```java
// Too broad: any string is a valid reason, whether it makes sense or not
Result<Job, String> result = new Failure<>("the query went wrong, somehow");
```

We already did better than this. We defined `JobLookupError` as a sealed interface with exactly two variants: `JobNotFound` and `DatabaseUnavailable`.

By using it as the type parameter `E`, we reduce the number of valid failure shapes to exactly two. There is no "what does this string mean?" question at runtime. The type itself tells us:

```java
Result<Job, JobLookupError> result = new Failure<>(new JobNotFound(id));
```

We replaced an unbounded `String` with a sum type, and the set of valid failure values went from infinite to two. Less is better.

:::tip
The compositionality of ADTs makes them a good fit for domain modeling. The `Job` product type appears inside `Found`. The `JobLookupError` sum type appears inside `Failure`.

We can keep composing without limit, building richer types from smaller ones, and the compiler keeps track of every invariant for us.
:::

## Conclusion

In this article, we introduced Algebraic Data Types in Java. We started with the pain of the traditional approaches: nullable fields that hide invalid states, and open class hierarchies that leave the compiler blind to missing cases.

We then established a shared domain vocabulary and introduced the two building blocks. We used records to express product types and sealed interfaces to express sum types.

We combined the two building blocks to create hybrid types, and we saw that the same pattern extends to the generic `Result<T, E>` type.

We covered switch expressions, pattern matching with instanceof and switch, and record patterns as tools for consuming ADTs. Record patterns let us destructure records inline, and the compiler enforces exhaustiveness over the closed set of variants.

We also explained what Java generics invariance means in practice and why both type parameters must appear on both Success and Failure.

We saw why these types are called "algebraic": records are products (AND), sealed interfaces are sums (OR), and we can compose the two to model any domain.

We showed how replacing a raw String with a sum type removes invalid states from the design.

The pattern is the same one used in Haskell, Rust, and Scala under different names. In Java 25, we have all the tools to apply it directly. **Illegal states should not be representable, and now they do not have to be.**
